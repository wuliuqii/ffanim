# ffanim 调研对比报告

> 项目：ffanim —— 基于 Rust + Typst + Vello 的 manim 替代品（数学动画引擎）
> 本报告是对现有方案（manim、fframes、Motion Canvas、Remotion、Ranim 等）的调研与分析，为《02-架构设计》提供依据。

## 2. 逐项深入分析

### 2.1 Manim CE —— 数学动画的语义标杆

**核心架构**

- **Mobject 树**：一切可视对象继承 `Mobject`，经 `submobjects` 组成父子树；`VGroup/Group` 负责组合与 `arrange/next_to` 布局。`VMobject` 用扁平 numpy 数组存贝塞尔曲线（锚点 + 控制柄），fill/stroke 样式直接挂在数据上。
- **动画系统**（最大精华）：
  - `Animation` 基类五段生命周期：`begin → interpolate(alpha) → finish → clean_up`；
  - `alpha ∈ [0,1] + rate_func` 构成完整时间模型；
  - `.animate` 链式语法"只写终态"（builder 生成 target 副本 → 应用方法 → 打包为动画）是公认好设计；
  - 组合三件套 `AnimationGroup(lag_ratio=0 并行) / Succession(=1 顺序) / LaggedStart(=0.05 错峰)` 用同一参数统一编排语义；
  - `updater / always_redraw / ValueTracker` 提供"数据绑定式"持续动画。
- **数学能力**：`MathTex` 经 TeX 模板 → latex + dvisvgm → SVG → 路径；`TransformMatchingTex` 用字符串最长匹配块逐段变形，`TransformMatchingShapes` 按几何形状相似度配对；`Axes/NumberPlane` 提供 `c2p/p2c` 坐标映射与函数图像。
- **渲染**：Cairo CPU 光栅化（默认）与 OpenGL 实时预览两条路径；"相机即 Mobject"（MovingCameraScene 的 frame 可动画）。

**已知痛点（新项目必须避开）**

1. **LaTeX 依赖地狱**：完整 TeX 发行版 + dvisvgm，容器环境脆弱；每条公式同步阻塞编译约 2 秒且无并发。
2. **渲染慢**：每帧全量重算 Python 对象 + Cairo 单线程光栅化，1080p 复杂场景单帧可达数秒。
3. **类型陷阱**：`VGroup` 只接受 `VMobject`、`Transform(A,B)` 后 A 仍在场景的可变引用陷阱。
4. **生态分裂**：CE 与 ManimGL API 互不兼容，双渲染器双类层级（`ConvertToOpenGL` 元类）是复杂度主要来源。
5. **预览迭代体验差**：靠 `-ql`、`-n` 跳动画等土办法。

**借鉴结论**：**抄** —— `self.play` 声明式时间轴、`.animate` 终态语法、`alpha + rate_func`、`lag_ratio` 三件套、updater 模式、`Create/Write/FadeIn` 动画词汇、`TransformMatchingTex`、`c2p/p2c`、相机即对象。**避** —— LaTeX 外部进程、双渲染器类层级、类型分裂、可变引用陷阱、逐对象绘制调用。

### 2.2 fframes —— Rust 工程管线的标杆

**核心架构**

- **每帧纯函数**：`trait Video { const FPS/WIDTH/HEIGHT; fn render_frame(&self, frame: Frame, ctx: &FFramesContext) -> Svgr }`，文档明确要求无 I/O、无 panic（渲染中途失败代价极高），动态数据预计算进 `self`。
- **渲染管线**：`svgr!` proc-macro 把 SVG 解析为节点树；开启 `compile-time-svgtree` 后语法树在编译期构造（运行时零解析），并对**不含插值的静态子树计算内容哈希**，渲染器按哈希复用已光栅化的子树位图 —— 这是其高性能的关键设计。
- **GPU 后端**：Skia（macOS=Metal，Linux/Windows=Vulkan），约 10 倍于内置 CPU 后端；后端以 trait 注入（`FFramesRenderBackend`），支持 SkSL/GLSL shader 层。
- **编码管线**：直接链接 libav（build.rs 下载预编译静态库，缺失则源码编译）；每 worker 领取连续帧段独立渲染+编码为 segment（保持缓存局部性），工作窃取调度，最后 concat 拼接；纯 Rust 音频 DSP（gain/pan/fade/ducking + lookahead limiter）。
- **Agent 工具链 CLI**（核心洞察：*作者无法看视频，把视频变成 PNG/文本/数字*）：
  - `inspect`：每 0.25s + 每场景首尾帧跑渲染诊断（缺字体/文字溢出/非法 SVG），exit code 2；
  - `strip`（接触表）、`onion`（洋葱皮显运动轨迹）、`frame`（全尺寸 PNG）、
  - `snapshot`（与已批准 PNG 像素 diff，可作测试断言）、`audio analyze`（LUFS/削波/静音）、
  - `preview`（GPU 实时窗口）、`render --draft`（半尺寸快速出片）；
  - 时间规格 DSL：`120f / 3.2s / 50% / SceneName@1.2s / a..b`。
- **发行策略亮点**：`cargo fframes new` 脚手架 + 官方 coding-agent skill（"框架即 skill"）；WASM 编辑器（浏览器时间轴）。

**已知局限（= ffanim 的机会缺口）**

1. **无数学排版**：只有 SVG `<text>`，无 LaTeX/Typst，无逐字形公式动画。
2. **无对象保留模型**：没有 mobject、没有 `Transform` 状态 morphing，一切动画退化为数值插值。
3. CPU 后端对 filter/shadow/gradient 极贵；文本排版只是辅助函数。

**借鉴结论**：fframes 证明了"Rust 程序化视频"的生产化路径（编译期缓存、libav 直链、agent CLI、纯函数渲染）。**功能层面它与 manim 不同赛道**，ffanim 的定位应是"manim 的数学语义 + fframes 的现代 Rust 工程化"。

### 2.3 Motion Canvas —— 时间轴与预览的标杆

- **生成器协程模型**：`makeScene2D(function*(){ yield* rect.position([0,0],[200,0],1s); })`，`yield*` 补间；编辑器逐帧跑生成器**预计算时间轴**（recalculate），实现可 seek 的精确预览与时间事件（与旁白对齐）。
- **借鉴结论**：其"构建期求值时间轴、渲染期纯查表"的两阶段模型，与 Rust 的所有权模型天然契合（见 02 文档 §3.2）；编辑器的可 seek 预览体验是标杆。

### 2.4 Remotion —— 不作为参照

每帧一次 React 渲染 + 无头浏览器截图，生态大但重且慢；许可证源可用（营收门槛收费）、5.0 起部分场景强制 telemetry。不适合作为开源数学动画引擎的参照。

### 2.5 Javis.jl —— 生态教训

Object-Action 范式，LaTeX 依赖外部 Node 进程（mathjax-node-cli）；生态小 + 重外部依赖导致传播受限。**教训**：公式排版必须进程内解决（Typst 嵌入），不能依赖外部工具链。

### 2.6 Rust 侧先例 —— 可行性与失败原因

- **Ranim**（0.1.x alpha）：与 ffanim 技术路线几乎相同（typst + wgpu + ffmpeg），验证了路线**走得通**；但 WIP、API 不稳、文档不全 —— 先发空间仍在。
- **fframes 作者自述**：API"显式冗长"导致多年未发布 —— 即**API/时间轴模型设计是最大瓶颈，而非渲染/编码**。这直接决定 ffanim 应把 API 设计置于最高优先级。
- **早期 manim-rs 等尝试均无后续**，失败原因归纳：LaTeX 依赖重、libav 链接复杂、API 难稳定 —— 三者在本方案中均有对应规避策略（Typst 嵌入、ffmpeg 子进程、时间轴两阶段模型）。
- **EffectCraft**：纯 Rust 自研编码器全家桶可行但工作量极端，不做。

## 4. 结论与机会定位

1. **市场空位**：manim 有数学语义但工程陈旧（LaTeX 依赖、慢、类型陷阱）；fframes 工程现代但无数学语义；两者之间不存在"数学语义 + 现代 Rust 工程化"的成熟方案。Ranim 路线相同但完成度低。
2. **技术可行性已被验证**：Ranim 验证 typst+wgpu+ffmpeg 路线；fframes 验证 Rust 视频生产化；Typst 0.15 的 `Frame/FrameItem` 中间表示和 Manim CE 0.21 已把 Typst 列为一等公式后端，均佐证方向正确。
3. **最大风险不在底层栈而在 API 设计**（fframes 作者教训），架构设计（02 文档）以"时间轴两阶段模型"为核心决策来应对。
4. **差异化创新点**：① Typst 增量排版缓存 + 字形级公式动画；② 静态场景内容编译/构建期缓存（借鉴 fframes 哈希缓存思想，适配 Vello Scene 复用）；③ 面向 AI Agent 的验证 CLI；④ 无外部依赖单二进制（无 TeX、无 Node、ffmpeg 自动下载）。
