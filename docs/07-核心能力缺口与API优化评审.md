# 07 - 核心能力缺口与 API 优化评审

> 状态：评审结论（2026-10-15）
> 前置文档：[01-调研对比报告](01-调研对比报告.md) / [02-架构设计](02-架构设计.md) / [03-路线图与风险](03-路线图与风险.md) / [05-manim功能差距清单](05-manim功能差距清单.md)

## 0. 评审背景与方法

**定位调整**：ffanim 从「manim 替代项目」调整为**面向数学物理等领域视频创作的底层核心基础库**。基于该核心衍生的 manim 服务化应用、类 GeoGebra 交互创作工具等上层产品形态**不纳入本次评估范围**——本评审只回答两个问题：

1. 作为专业渲染引擎 + 数学物理内容创作的底层库，核心能力还缺什么；
2. 当前 API 设计是否让「手写一段数学动画」付出不必要的代码成本。

**评审输入**：

- 门面公开 API 56 项（`scripts/api_coverage.sh` 口径）；
- 9 个示例文件共 3156 行（含 37 个场景画廊场景），全部通过门禁与抽帧验收，是「真实用户视角」的最佳证据；
- 架构宪法（02 文档）与 M0~M9 全部里程碑结论。

**已具备能力基线**（以下不列为缺口）：vello GPU 主路径 + vello_cpu 兜底、ffmpeg rawvideo 管道、质量预设与多 codec（codec 字符串透传）、片段导出（`render_to_mp4_frames`）、分段并行帧渲染、strip/onion 视觉诊断、Typst 公式排版 + LRU 缓存 + CJK 字体探测、Axes 双向坐标变换（c2p/p2c）、Tracker/updater、布尔路径运算（i_overlay）、SVG/图片导入、BGM 混流与音频分析、TransformMatchingShapes/Tex、组动画 `group`/`add_group`、`benches/render.rs`。

**优先级标记**：P0 = 阻断核心创作流程或改动极小收益极大；P1 = 核心场景受限，影响大；P2 = 体验/生态增强；P3 = 远期。
**影响程度**：高 = 数学物理视频的核心叙事手段缺失；中 = 常用但可拼装绕行；低 = 锦上添花。

## Part II 优先级汇总与依赖关系

**P0（四项，全部「小改动、大解锁」）**：

1. **1.1 裁剪/蒙版原语** —— 解锁透镜/区间显示等高频叙事手段

## Part III API 设计评审

### III.1 现状量化：冗余在哪里（硬数据）

对 9 个示例文件（3156 行、37 场景）做模式统计：

| 模式 | 出现次数 | 说明 |
|------|---------|------|
| `with_transform` | 35 | 上屏必带，与 `to_items`/`fit_transform` 组成三步曲 |
| `.map(\|&id\| ...)` 编排映射 | 29 | ids 收集 + `tl.group` 前置样板 |
| theme 取色（`foreground/accent` + `?`/`unwrap`） | 36 | `Result<Color>` 泄漏到每个调用点 |
| `.during(...)` | 178 | 高频但语义明确（显式时长），**不算冗余** |
| `fit_transform` | 20 | 其中 **9 处手写 `scale = 2.0`（pt→px 魔法数）** |
| `to_items()` | 17 | 拆件三步曲第一拍 |
| `tl.group(` | 22 | 组动画排入 |
| `find_cjk_font` + `add_font_face` | 22 + 6 | 字体注入样板，逐文件重复 |
| `TypstEngine::new` | 15 | 引擎装配样板 |
| `FormulaOptions {` / `TextOptions::new` | 7 + 12 | 选项结构逐处构造 |
| `Theme::from_path` | 8 | 每文件 1 次纯样板 |
| 多场景入口样板（`SCENES` + `build` + `main` argv 分发） | 5 份同构 ≈35 行/份 | gally 依赖此形态，可保留 |

**单场景长度**：`basic.rs` 1416 行 ≈ 54 行/场景；`typography.rs` 442 行 ≈ 88 行/场景（含文件级样板）。其中环境装配 + 三步曲 + ids 收集合计约占每场景 30%~40% 行数，**与场景的数学内容无关**。

### III.2 冗余根因（5 条）

**R1 无环境装配入口（最重）**。库直接暴露全部底层原语，但没有任何「开箱即用」收敛层。每个示例 main 重复装配四件套：`Theme::from_path` → `TypstEngine::new` → `find_cjk_font`/`add_font_face` → `Timeline::new(w, h, fps, theme.background()?)`，约 12 行 × 9 文件。manim 的 `Scene` 基类、Motion Canvas 的 `view`、GUI 框架的 environment 承担的正是这一职责。

**R2 文本/公式上屏无一步 API**。最高频复合模式：`engine.text()/formula()` → `to_items()` 拆件 → 逐件 `add` + `with_transform(place)` → `group(map(Anim::create), step)`。四拍全由用户手工拼，且 `place` 需要用户持有 Affine 语义。这是 17+20+29 处样板的共同源头。

**R3 `Theme` 取色返回 `Result`，且 `Timeline` 不吃 `Theme`**。`ColorSpec::parse` 的失败只可能来自 JSON 配置错误，理应在 `Theme::from_path` 一次性报错；现在却泄漏成每个调用点的 `?`/`unwrap`（36 处）。同时 `Timeline::new` 只吃 `background: Color`，风格参数（style/fg/accent）只能散落传参。

**R4 pt→px 单位换算外溢**。Typst 是 pt 世界、画布是 px 世界，`fit_transform(cx, cy, 2.0)` 的魔法数出现 9 处。缩放语义应由库定义（如「目标像素高度」），而不是用户推导。

**R5 组动画 ids 收集样板**。`let ids: Vec<_> = items.map(add).collect(); tl.group(ids.iter().map(|&id| Anim::create(id)...), step)`。`Timeline::add_group` 已存在但只解决收集不解决编排联动，且大量示例未使用（仅 9 处）——API 存在性与可发现性双重问题。

**非问题澄清**：`.during` 显式时长（178 处）是「显式优于隐式」的正确设计，manim 同样要求显式 `run_time`；多场景 argv 分发样板是示例组织形态（gally 解析依赖），不属库 API 问题。

### III.3 对比主流范式

| 库 | 环境装配 | 一步上屏 | 默认时长/缓动 |
|----|----------|----------|---------------|
| manim（Python） | `Scene` 基类持有 camera/config | `self.play(Write(Tex("...")))` 一行 | config 全局默认 |
| Motion Canvas（TS） | `view` 上下文对象 | `view.add(<Text/>)` 节点声明 | 信号系统管理 |
| SwiftUI/Flutter | environment 注入 | 叶子组件一行声明 | 框架默认 |

共同结论：**成熟动画库都有「上下文对象收敛环境装配」+「声明式一步上屏」**，底层原语（节点/Item）与糖层分离。ffanim 现状 = 只有原语层，糖层为零——这正是「单场景源码过长」的结构性原因，也验证了最小原语架构本身没有错（37 场景全部拼装成功、硬缺口清零），缺的只是**糖层**。

### III.4 设计问题清单与优化方案

**方案总原则**（约束检查表，每条方案须通过）：

1. 糖层纯组合器：只做已有原语的编排封装，**零新渲染能力**；
2. 原语层 API 完全不动，糖层可整体绕过（服务化/交互上层直接用原语层不受影响）;
3. 单向依赖：糖层 → 原语层，原语层不知晓糖层存在。

**D1（对应 R1+R3）新增 Stage 便捷层**——核心方案：

```rust
/// 糖层：环境装配 + 一步上屏。位于独立 module（如 ffanim::stage），
/// 不使用则零成本，原语层不受任何影响。
let mut stage = Stage::from_theme_path("themes/default.json", 960, 540, 30)?;
// 内部完成：Theme 加载+解析、TypstEngine 装配、CJK 字体探测注入、
// Timeline 构造（吃 theme.background 与 theme.style）

// 文本/公式一步上屏：排版→拆件→落位→add 全收敛，返回可动画句柄
let title = stage.text("傅里叶级数与方波", 52.0)?;        // 默认画布居中顶部，px 语义字号
let f = stage.formula("f(x) = 4/pi (sin x + dots)", 30.0)?; // 高度/位置可选参数

// 组动画一行排入（替代 collect+map 三行）
stage.write(&title).during(1.0);                  // 逐字形 Create
stage.write_all(&[&f1, &f2], 0.06);               // 组内错峰

// 逃生舱：原语层随时可达
let tl: Timeline = stage.into_timeline();
let id = tl.add(Item::circle(...));               // 原语照用
```

- `Stage` 持有 `Theme`（解决 R3 的风格散落）与 `TypstEngine`（解决字体装配）；
- `stage.timeline()`/`into_timeline()` 逃生舱保证糖层永不成为天花板；
- 服务化上层可直接用原语层做模板批量渲染，交互上层可用原语层 + 自己的 UI 状态——**不构成任何限制**。

**D2（对应 R3）Theme 解析前置**：`from_path` 时把 `ColorSpec` 全部解析为 `Color` 缓存；`foreground()/accent()/background()` 改返回 `Color`（无 `Result`）。pre-1.0 一次性 breaking，36 处 `?`/`unwrap` 全部消失；配置错误在加载点一处报错，语义更准确。

**D3（对应 R4）落位意图 API**：`Formula` 增加 px 意图构造——`to_items_at(cx, cy, font_px)`（内部由 `font_px/源pt` 推 scale），`fit_transform` 保留为 Affine 逃生舱。9 处 `2.0` 魔法数归零，D1 的 `stage.text/formula` 内部即用它。

**D4（对应 R5）组动画排入 API**：`tl.animate_group(&[ItemId], |id| Anim::create(id), step)`（或 Stage 版 `write_all`），一行替代 collect+map 样板；`add_group` 文档补位提升可发现性。

**D5（对应能力缺口 3.1）速率函数开放**：`tl.register_rate(name, f64->f64) -> RateFunc`（注册表变体，保持 `Copy`/序列化语义），`RateFunc::Smooth` 等内置项不变。

## 结论

1. **能力侧**：最小原语架构已通过 21 例 manim 对照全部清零的实证，核心缺口收敛为四个 P0 小改动项（clip、ODE、自定义速率、PNG 序列）与一条 P1 主线（线代→3D）；交互 UI 与 CAS 明确列为非目标，与本库定位一致。
2. **API 侧**：冗余的结构性根因是「只有原语层、没有糖层」，而非原语设计有误。新增可绕过的 Stage 便捷层 + 四项局部收窄（Theme 解析前置/落位意图/组动画 API/速率开放），同等效果代码量预估下降 20%~40%，且不构成对上层产品形态的任何限制。
